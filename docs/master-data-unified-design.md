# 基础资料（主数据）统一设计

> 目标：对齐**金蝶「基础资料」的设计理念** —— 基础主数据统一管理，后续各业务子系统都基于它构建。
> 本文把金蝶的基础资料模型映射到本仓库，给出**归口、编码、分配、引用、建档**五个方面的改造方案。
>
> 状态：**一期（菜单归口）已落地**（2026-10），见 §6；二~四期待做。相关：[intelligent-system-blueprint.md](./intelligent-system-blueprint.md) §4（主数据统一）、
> [organization-architecture-design.md](./organization-architecture-design.md)（组织架构与门店类型）、
> [organization-model.md](./organization-model.md)（一店三面）。

## 0. 先纠一个常见误解

「模仿金蝶 = 把主数据合并成一张表 / 一切以组织架构为核心」是**不成立**的。金蝶本身的做法恰恰相反（见 §1）。
**统一的是平台与机制（入口、编码、分配、引用），不是实体。**

## 1. 金蝶的模型（有出处，不凭记忆设计）

来源：[金蝶云产品手册 · 基础设置](https://help.open.kingdee.com/dokuwiki/doku.php?id=%E5%9F%BA%E7%A1%80%E8%AE%BE%E7%BD%AE)

### 1.1 结构

```
基础设置
├─ 基础资料
│   ├─ 主数据        部门 · 员工 · 供应商 · 客户 · 物料      ← 五个并列的独立对象
│   ├─ 公共资料      币别 · 计量单位(组) · 存货类别 · 成本中心 · 费用项目 · 岗位 · 业务员 …
│   ├─ 单据类型
│   ├─ 财务会计      汇率体系 · 会计日历 · 银行 · 银行账号 · 其他往来单位 …
│   ├─ 税务管理      税收制度 · 税种 · 税率 · 税组合
│   ├─ 供应链        仓库 · 仓位值
│   └─ 辅助属性 / 辅助资料 / 多语言 …
├─ 公共设置（参数、单据设置、国际化…）
└─ 业务初始化
```

手册原文定义：

> 「基础资料是在系统中使用的各种基础数据的总称……**所有的凭证、单据都是由一些基础资料信息和具体的
> 数量信息构成的**。对于这些基础的数据，为了便于进行**统一的设置与管理**，我们提供了基础资料管理
> 这样一个功能。」
>
> 「基础设置是**各业务应用的公共平台**，是各领域的应用基础」「为各业务领域的设置提供了**统一入口**，
> 以便管理员集中设置，统一管理」

### 1.2 两个关键机制（这才是要模仿的东西）

1. **统一入口**：所有主数据在一个平台集中维护，子系统只引用；
2. **分配型 + 组织内编码唯一**：
   > 「预置基础资料都是**分配型**，保存校验按**组织内编码唯一**来进行校验，适用多组织应用场景」

   即：**组织（部门树）是主数据的归属维度与校验范围，不是主数据的容器。** 客户挂在组织下，但客户 ≠ 组织。

**结论：「部门」和「客户」在金蝶里是并列的两个主数据对象，共享同一套管理平台，各自有独立属性集。**

## 2. 判断规则（本文的方法论）

> **同一个概念的两套目录 → 合并；不同概念的实体 → 并存 + 绑定。**

这条规则不是本文发明的，[intelligent-system-blueprint.md](./intelligent-system-blueprint.md) §4 已经在按它走：

| 蓝图条目 | 处理 | 依据 |
|---|---|---|
| §4.1 商品 | **合并** | `erp_product`（一物料一单位）与 `product_spu`+`product_sku` 是**同一个概念的两套目录** |
| §4.2 门店档案 | **并存 + 绑定** | 门店 = dept 节点（组织）+ `erp_customer`（经营结算）→ 一店三面 |
| §4.3 价格 | **并存** | ERP 基础价 + 独立「价格政策」表，取价优先级分层 |
| §4.6 其他 | **ERP 维护，商城只引用** | 仓库货位、计量单位、商品分类、结算账户 |

## 3. 现状盘点（全部实测）

### 3.1 金蝶主数据 ↔ 本仓库承载

| 金蝶基础资料 | 本仓库承载 | 所在模块 / 页面 | 状态 |
|---|---|---|---|
| **部门** | `system_dept` | system · `views/system/dept` | 有；**缺类型**（组织/门店）与开店闭店 |
| **员工** | `system_users`（`AdminUserDO`） | system · `views/system/user` | 有 |
| （订货账号） | `member_user` | member · `views/member/user` | 有；**未纳入基础资料归口** |
| **客户** | `erp_customer` | erp · `views/erp/sale/customer` | 有；**无业务编码** |
| **供应商** | `erp_supplier` | erp · `views/erp/purchase` | 有；扩展方案见 [supplier-master-data-design.md](./supplier-master-data-design.md) |
| **物料** | ⚠️ **两套**：`erp_product` 与 `product_spu`+`product_sku` | erp · mall | **待合并**（蓝图 §4.1） |
| 仓库 | `erp_warehouse` | erp · `views/erp/stock` | 有；无仓位（货位）概念 |
| 计量单位 | `erp_product_unit` | erp | 有 |
| 商品分类 | ⚠️ **两套**：`erp_product_category` 与 `product_category` | erp · mall | **待定权威** |
| 结算账户 | `erp_account` | erp · `views/erp/finance` | 有 |
| 币别 | `fms_currency` | fms | 有；但 ERP 单据未使用多币别 |
| 税率 | 无独立主数据，作为字段挂在往来对象上（`ErpCustomerDO.taxPercent`、`ErpSupplierDO.taxPercent`） | — | 缺 |
| 仓位值 / 成本中心 / 费用项目 | 无 | — | 缺 |
| 财务公共资料 | `fms_account_set`（账套）、`fms_auxiliary_type`/`fms_auxiliary_item`（辅助核算）、`fms_subject_template`（科目模板） | fms | 有；**未纳入统一归口** |

### 3.2 菜单归口现状：散在四处

后台一级菜单（对应 `apps/web-antd/src/views`）：

```
系统管理 → 部门管理（= 组织）· 用户 · 岗位 · 字典 · 租户 …
ERP      → 销售 → 客户管理 ｜ 采购 → 供应商 ｜ 商品 ｜ 库存 → 仓库 ｜ 财务 → 账户
商城系统 → 商品管理（与 ERP 商品是两套）
财务管理 → 账套 · 科目 · 辅助核算 · 币别
```

**没有金蝶那种统一的「基础资料」入口。** 同一个主数据对象分散在不同业务模块的菜单下，
维护人需要记住「客户在销售的菜单里、供应商在采购的菜单里」。

### 3.3 差距清单

| # | 差距 | 实测依据 |
|---|---|---|
| **G1** | **全部主数据没有业务编码** | `erp_customer` / `erp_supplier` / `erp_warehouse` / `erp_product_unit` / `product_spu` 的字段只有 `name` + `status`（+ `taxNo`）；唯一像编码的是 `product_sku.barCode`，但那是**条形码不是内部编码**。全部靠自增 `id` 引用、靠 `name` 人工识别。**这是与金蝶差距最大的一条** |
| G2 | 无统一入口 | §3.2；金蝶是「一个平台集中维护，子系统只引用」 |
| G3 | 无组织分配/隔离规则 | `erp_customer.dept_id` 已有，但**无唯一性约束、无按组织隔离**；金蝶是「分配型 + 组织内编码唯一」 |
| G4 | 两套目录未合并 | 物料（`erp_product` vs `product_spu/sku`）、商品分类（`erp_product_category` vs `product_category`） |
| G5 | 建档不是原子动作 | 「建门店」= 建组织节点 + 建 `erp_customer` + 互绑，三个手工步骤（`ErpCustomerServiceImpl` 里零 dept 逻辑） |
| G6 | 引用规范未成文 | 跨模块有 `*-api` 约定（如 `juling-module-erp-api`），但「禁止直连他模块表」没有落成书面纪律 |

## 4. 改造方案

### 4.1 统一入口（第一步，零数据模型改动）

新增一级菜单「**基础资料**」，把散落的主数据收进去。**只改菜单与页面挂载位置，不动任何表。**

```
基础资料
├─ 主数据
│   ├─ 组织架构       （部门 + 门店类型 + 开店闭店）      ← 现 系统管理/部门管理
│   ├─ 员工与账号     员工（system_users）+ 订货账号（member_user）
│   ├─ 客户           （= 门店档案）                      ← 现 ERP/销售/客户管理
│   ├─ 供应商                                             ← 现 ERP/采购/供应商
│   └─ 物料           （SPU/SKU，与 ERP 商品合并后）      ← 现 商城系统/商品 + ERP/商品
├─ 公共资料
│   ├─ 计量单位 · 商品分类 · 仓库与货位 · 结算账户
│   └─ 币别 · 辅助核算 · 账套（FMS 侧）
└─ 编码规则
```

**收益**：维护人只需记住一个入口；「基础资料」与「业务单据」在信息架构上分开，与金蝶一致。
**成本**：菜单数据 + 路由归属，无表结构改动。**建议作为独立的第一步先做。**

### 4.2 统一编码（G1，与金蝶差距最大）

给每个主数据对象加业务编码列，与自增 `id` **并存**：

| 对象 | 新增列 | 编码规则（示例） | 唯一性 |
|---|---|---|---|
| `erp_customer` | `code` | `KH` + 6 位流水（KH000001） | 租户内唯一 |
| `erp_supplier` | `code` | `GYS` + 6 位 | 租户内唯一 |
| `erp_warehouse` | `code` | `CK` + 4 位 | 租户内唯一 |
| `erp_product_unit` | `code` | 手工（个 / 箱 / kg …） | 租户内唯一 |
| `product_spu` | `code` | `WL` + 6 位 | 租户内唯一 |
| `system_dept` | `code` | `MD` + 4 位（门店）/ `BM` + 4 位（组织） | 组织树内唯一 |

**设计原则**：

- **`id` 做外键，`code` 做人对人**：数据库关联一律用 `id`（不改现有外键），
  `code` 用于界面展示、导入导出、跨系统对接、口头沟通；
- **编码建档后不可改**，只读；
- **组织内唯一**：对齐金蝶「组织内编码唯一」的校验口径。

`code` 生成走一张**编码规则表**（对齐金蝶的「编码规则」），而不是散在各个 service 里拼字符串。

### 4.3 统一分配与隔离（G3）

- 每个主数据对象明确**归属组织字段**（`dept_id`）；客户 / 供应商 / 仓库已有或可补；
- **校验**：同一组织内 `code` 唯一；
- **隔离**：数据权限按组织过滤时，主数据也纳入（今天 ERP 主数据没有任何按组织隔离；
  member 模块 0 处 `@DataPermission`）。

### 4.4 统一引用（G6）

把已有约定落成书面纪律：

1. 跨模块**只经 `*-api` 接口**读主数据（`juling-module-erp-api` 已有 `ErpCustomerApi` /
   `ErpProductApi` / `ErpStockQtyApi` 等；供应商按
   [supplier-master-data-design.md](./supplier-master-data-design.md) 新增 `ErpSupplierApi`）；
2. **禁止直连他模块的表**（跨模块只能依赖 `*-api`，依赖方向由 Maven 体现）；
3. 业务单据**存 `id` 引用 + 必要快照**：单据上冗余名称 / 价格快照是允许的（历史可追溯），
   但**不允许把主数据的可维护属性复制成第二个维护点**。

### 4.5 建档动作收敛（G5）

「建门店」收敛为**一个事务**：建组织节点（`dept_type = STORE`）+ 建 `erp_customer`
（`dept_id` 回指）+ 互绑。这是「主数据一起管理」在操作层的体现，也是消除当前重复录入的根治办法。
详见 [organization-architecture-design.md](./organization-architecture-design.md) §6 第 3 步。

## 6. 一期落地记录：菜单归口（2026-10）

**脚本**：[sql/local/55_master_data_menu.sql](../sql/local/55_master_data_menu.sql) —— **实测连续执行 3 次结果一致**。

```
基础资料 (12180, /master-data)
├─ 主数据   (12181, /md)      组织架构管理 · 客户信息 · 供应商信息 · 产品信息 · 订货账号列表
└─ 公共资料 (12182, /common)  产品分类 · 产品单位 · 仓库信息 · 结算账户
```

只改菜单（`parent_id` / `sort`）+ 补授权，**不动任何表结构、不动任何 API 路径**：
前端页面按菜单的 `component` 挂载（如 `system/dept/index`），与菜单 `path` 无关 ——
已 grep 确认前端只有 `#/api/...` 形式的 API 导入，**没有硬编码菜单路由**。

**已补祖先链授权**：yudao 会剔除父菜单未授权的节点，所以把新目录授给「原本就拥有被迁菜单」的
3 个角色（普通角色 / 财务 / 供应链），否则迁过去就看不见了。

**刻意没迁的两处**（留在原地，避免「只搬一半更乱」）：

| 目录 | 为什么不迁 |
|---|---|
| 商城系统 → `商品中心(2000)` | 与 ERP「产品管理」是**两套重复的物料目录**，合并（二期）时一并归口 |
| WMS 系统 → `基础数据(6210)` | 同上：与 ERP 的仓库 / 商品重复 |

## 7. 三期落地记录（第一步）：编码规则与存量回填（2026-10）

**脚本**：[sql/local/56_code_rule.sql](../sql/local/56_code_rule.sql) —— **实测连续执行 3 次结果一致**（43 条语句零失败）。

| 动作 | 内容 |
|---|---|
| 规则表 | 新建 `system_code_rule`（`rule_key` / `prefix` / `seq_length` / `current_value`），对齐金蝶的「编码规则」 |
| 加列 | `erp_customer` / `erp_supplier` / `erp_warehouse` / `erp_product_unit` / `product_spu` / `system_dept` 各加 `code varchar(32)` |
| 回填 | 按 `id` 升序 + 规则表里的 prefix/seq_length 拼接，**存量全部有码、0 条为空** |
| 唯一性 | `(tenant_id, code)` 部分唯一索引（`deleted = 0 AND code IS NOT NULL`） |
| 规值对齐 | `current_value` 回填为各表已用编码的流水最大值（实测 KH=15 / GYS=4 / CK=16 / DW=7 / WL=26 / BM=66） |

实测样例：客户 `KH000001, KH000002, KH000003`；组织节点 `BM0001, BM0002, BM0003`。

**两处与本文前面的设计有偏差，是有意的**：

1. **唯一性取租户内唯一，而非「组织内唯一」** ——「多组织」在本系统尚未成立
   （品牌算不算组织仍是 §8 的待确认项），先按租户内唯一落地，等组织维度定了再收紧；
2. **`system_dept` 统一用 `BM` 前缀**，不再按门店/组织分裂成 `MD`/`BM` ——
   节点类型已由 `dept_type` 精确表达，编码前缀保持单一更稳定。

**`code` 允许为 NULL**（唯一索引带 `code IS NOT NULL` 条件）：新建路径尚未接入编码生成时
不会因 NOT NULL 直接插入失败。**因此还差两步才算完成**：

| 待做 | 说明 |
|---|---|
| 生成服务 | system 模块的 `CodeRuleService#generateCode(ruleKey)`（`SELECT … FOR UPDATE` 串行化规则行，避免并发重码）+ 各主数据 create 路径接入 |
| 界面 | 各主数据列表/表单展示并允许查看编码（金蝶的编码是人工可识别的引用键） |

## 8. 待确认

1. **主数据维护权归谁**：金蝶按业务领域分权（客户归销售、供应商归采购、物料归商品）。
   本仓库沿用「谁用谁维护，但入口统一」，还是集中到「主数据管理员」角色？
2. **编码是否允许人工录入**：金蝶允许建档时录入编码。人工可编辑的好处是能对齐现有线下台账，
   代价是要处理重码与改码；全自动生成则简单但对接旧台账时要额外映射。
3. **多组织是否真的存在**：「组织内编码唯一」在单组织下等价于全局唯一。
   亚特是多品牌（卤校长 / 萍姐 / 杨老头 / 耙二哥 / 直营），**品牌算不算「组织」**决定 G3 的实现复杂度。
4. **物料合并的权威目录选哪个**：蓝图 §4.1 取 `product_spu`/`product_sku` 为权威、ERP 侧改为 SKU 维度。
   这是一次伤筋动骨的迁移，需要与采购 / 库存 / 成本一起排期。
5. **`erp_product_category` 与 `product_category` 哪套权威**（这是物料合并的前置问题）。
