# 智能管理系统蓝图（替代金蝶 · 业务审批 · AI 智能）

> 状态：Phase 0 草案，待评审
> 决策输入（2026-09-28）：① 全部替代金蝶，长期不再使用；② 主数据统一以长期维护为准；
> ③ 门店订货先款后货，未来采购链供应商支持多种账期；④ AI 用云端 API（DeepSeek，模型 `deepseek-flash`）。

## 1. 目标

把现有系统从「订货商城 + 付款核验」升级为**唯一的经营主系统**：门店要货申请 → 供应链/财务审批 →
销售出库 → 应收与收款核销 → 采购与应付 → 总账报表，全链路可审批、可追溯，并由 AI 承担审核辅助、
智能下单与经营问答。金蝶在并行一个账期后退役。

## 2. 现状盘点（实测）

| 底座 | 状态 | 说明 |
|---|---|---|
| 商城（trade） | **在用** | H5 门店下单、线下转账 + 付款凭证核验（可部分收款）、快递发货、确认收货；订单状态 4 态（0 待支付/10 待发货/20 已发货/30 已完成/40 已取消），收款是独立维度（`payment_proof_status` + `paid_amount`） |
| 审批（bpm） | 可用未用 | Flowable 引擎与 40 张 `act_*` 表 + 7 张 `bpm_*` 表均已建；CRM 合同审批、HRM 请假已接入；PC 有流程设计器与待办页，员工端 App 有审批页 |
| ERP | 空壳 | 33 张单据/主数据已具备（销售订单/出库/退货、采购订单/入库/退货、库存/流水/盘点/调拨/其他出入库、收付款单、客户/供应商/仓库/账户/产品）；现仅 1 条演示数据 |
| AI | 空壳 | 聊天、知识库(RAG)、模型管理、工具调用、AI 工作流、绘图/写作/思维导图齐全；`ai_model`/`ai_api_key`/`ai_knowledge`/`ai_workflow` 均为 0 行 |
| 组织与角色 | 已具备 | 「供应链」(gyl/gyl_zy)、「财务」(cw) 角色已建；租户体系可用 |

**结论**：缺的是业务梳理与数据打通，不是代码底座。

## 3. 替代范围与分期

全部替代金蝶，分三段推进（总账/税务放在最后，且必须先解决合规留痕）：

| 阶段 | 覆盖范围 | 依据 |
|---|---|---|
| 一期 | 销售（要货→销售订单→销售出库→退货）+ 库存（出入库/调拨/盘点/流水）+ 应收与收款核销 | ERP 已具备单据；商城已在跑 |
| 二期 | 采购（申请/订单/入库/退货）+ 应付与付款 + 存货成本（加权平均/批次/效期） | ERP 骨架已具备，需补核算规则 |
| 三期 | 总账与凭证、报表、税务、固定资产 | **FMS 总账已有底子**（见 4.6），需补齐凭证自动化、期初余额、报表模板与税务/资产；合规与审计要求最高 |

## 4. 主数据统一（长期维护视角）

### 4.1 商品：物料 + SKU 两级模型（关键改造）

现状冲突：ERP 产品是「一物料一单位」（`erp_product`：name/barCode/categoryId/unitId/standard(规格字符串)/
purchasePrice/salePrice/minPrice），**没有 SKU**；商城是 SPU + SKU 多规格（`product_spu` + `product_sku`，
含 price/market_price/cost_price 单一定价与库存）。两个目录并存无法算准库存与成本。

**方案（长期）**：统一为「物料 + SKU」两级，SKU 作为库存与单据的最小单位。

1. 以 `product_spu` 为物料主数据（商品中心），`product_sku` 为 SKU 主数据；
2. ERP 单据明细由 `productId` 扩展为 `productId + skuId + unitId + count`（销售订单/出库、采购、库存、盘点、调拨）；
3. 库存表由物料维度改为 **SKU 维度**（`erp_stock`/库存流水按 skuId，支持批次与效期列）；
4. 商城商品维护入口与 ERP 商品中心**合并为一处**（一处建档、商城只维护上架/展示属性）；
5. 迁移路径：先建 SKU↔ERP 产品映射并**双写**（商城下单同时写 ERP 单据），库存核对一致后切换为单一目录。

### 4.2 门店档案 = ERP 客户

门店（加盟店）在 ERP 建为客户（`erp_customer`），带业务员、结算方式、账期、信用额度；
商城会员与客户档案建立一对一关联，下单时校验额度与账期。

**补充（已核实的现状与三面绑定）**：加盟店**本来就维护在部门树上**（`system_dept` 134–146 共 13 家门店，
公司层 128/131，采购部门 = dept 163），全库没有独立"组织/公司"表。但门店的三张面目前**是断的**：
`trade_order` 只有 `user_id`、`erp_customer` 没有 `dept_id`、`member_user` 也没有 `dept_id` ——
"给加盟店开账号去 H5 订货"在数据上链不起来（不知道是哪家店、该记谁的账）。落地即
**一店三面**：dept 节点（权限/审批归属）+ `erp_customer`（店型/账期/信用/配送价，补 `dept_id`）
+ `member_user`（H5 订货账号，补 `dept_id`/`customer_id`），下单时把两者快照进 `trade_order`。
详见 [`docs/organization-model.md`](./organization-model.md)。

### 4.3 价格政策（长期可维护的正道）

ERP 的产品价（成本价/销售价/最低价）作为**基础价**，商城侧的客户等级价、阶梯价、促销价独立成
「价格政策」表，取价优先级：**客户协议价 > 等级价 > 阶梯价 > 标准售价**。避免把促销逻辑塞进商品主数据。

> 现状更正：商城目前**没有**阶梯价、客户等级价或协议价表（`product_sku` 仅 price/market_price/cost_price
> 三个单值），上述"价格政策"属于要新建的能力，不是既有功能。
>
> **配送价目表（采购部门需求：价差/毛利率、毛利异常提醒、历史售价）**：`erp_delivery_price` 版本化主表
> + 与采购成本账本按日期 join 出历史毛利曲线 + `erp_price_alert_record` 统一预警（成本涨幅/毛利过低/倒挂）。
> 完整设计见 [`docs/delivery-price-list-design.md`](./delivery-price-list-design.md)。

### 4.4 供应商主数据扩展（采购部门在途需求）

`erp_supplier` 已有 `taxNo / taxPercent / bankName / bankAccount / bankAddress`（单账户），并被 19 个文件
引用（采购订单/入库/退货、付款单、其他入库单）；缺**是否可开票、结账方式、多账户、合同×组织、交期**。

落点：扩展列（开票资质、发票类型、结账方式、账期天数/结算日、承诺交期、合作状态、证照）
+ 子表 `erp_supplier_account`（多账户，含默认账户与币种）+ `erp_supplier_org_contract`（合同 × 组织，
即"签订了哪几个组织"）。**新建 `juling-module-erp-api` 暴露 `ErpSupplierApi`**，供报销/财务/计划统一读取，
不直连表。完整设计（含分期与待确认项）见 [`docs/supplier-master-data-design.md`](./supplier-master-data-design.md)。

### 4.5 采购成本与价格历史（采购部门在途需求）

金蝶的采购价目表是**档案式**（覆盖写，只剩最新成本），而本系统采购单据明细本就带
`product_price / tax_percent / tax_price` 与供应商、日期 —— "商品→供应商→日期→价格"的流水一直在库里，
只是从未被当作价格历史查询。方案是补一张**只追加的价格流水账本** `erp_product_cost_history`
（含旧价/差额/涨幅、变动原因、变动人、来源单据），四处写入钩子：采购订单审核、采购入库审核、
商品档案改价、手工调价/成本卡录入。在此之上做三个视图与三张表：历史曲线与跨年趋势（ECharts）、
成本异动（旧价/新价/差额/涨幅）、波动预警（`erp_cost_alert_rule` + 记录 + 站内信）、降本标记
（`erp_product_cost_tag`）、成本卡（`erp_cost_card`，标准成本差异）、配送价检查清单。
完整设计见 [`docs/purchase-price-history-design.md`](./purchase-price-history-design.md)。

### 4.6 其他主数据

仓库与货位、计量单位与换算、商品分类、结算账户（`erp_account`）——均由 ERP 侧维护，商城只引用。

### 4.7 财务主数据与总账（现状澄清）

`juling-module-fms` 已是可用总账：会计科目 94 条、账套 1 个、辅助核算类型 7 类、凭证模板与凭证表齐备
（库里已录 2 张凭证），并有资产负债表/利润表/现金流量表与结账（`Closing*`）。**因此三期不是"从零做总账"**，
而是补三件事：① **ERP 业务单据自动生成凭证**（当前全库 0 处调用 = 金蝶替代的最大缺口）；
② 期初余额（`fms_initial_balance` 目前 0 行）与报表模板；③ 税务与固定资产。技术上同样需要
**`juling-module-fms-api`** 供 ERP 调用（或由 FMS 监听 ERP 单据事件）。

## 5. 单据链与状态

```
门店要货申请单（商城订单，新增审批维度）
   │ 供应链审核（可改数量/删行，重算金额并快照应收）
   │ 财务审核（核对应收与到账，复用现有付款凭证核验）
   ▼
ERP 销售订单 ──► ERP 销售出库（审核即扣库存，可分批：outCount）──► 发货配送 ──► 门店签收
   │                                              │
   └──────────► 应收单 ──► 收款单（核销收款凭证）──┘
退货：门店申请 ──► 售后审批 ──► 销售退货（回库存/冲应收）
采购：采购申请 ──► 采购订单（供应商账期）──► 采购入库（应付）──► 付款单
库存动作：其他出入库、调拨、盘点（均带审核态）
```

与现状的映射：商城订单继续作为「要货申请单」；现有 `payment_proof_status`/`paid_amount` 升级为
**收款核销**的明细来源；订单审核通过后创建 ERP 销售订单与销售出库，出库审核通过时扣库存。

## 6. 审批流（Flowable 混合式）

- 引擎复用现成 BPM：PC 端流程设计器 + 待办页、员工端 App 审批页，无需另做待办中心；
- 一期流程 `mall_order_approve`：发起（门店提交）→ 供应链审核 → 财务审核 → 结束；
  任务分配按角色（供应链 / 财务），未来金额阈值加签用条件分支配置；
- **边界**：BPM 只负责「轮到谁 / 通过 / 驳回 / 留痕 / 待办」；业务校验与计算（库存可用量、金额重算、
  应收快照、信用额度、收款是否满足）全部在 trade / erp 内完成；
- ERP 单据自带 `ErpAuditStatus`（10 未审核 / 20 已审核），审核即过账（销售出库审核通过才扣库存）；
  流程结束事件写入该状态，二者职责分明；
- 订单新增字段：`process_instance_id`、`audit_status`（0 待供应链审核/1 待财务审核/2 已通过/3 已驳回/4 已取消）、
  `receivable_amount`（应收快照）；
- 后续流程复用同一套：退货审批、调价审批、采购申请、费用报销；**反审核**（退回原点）在流程设计里预留。

## 7. 账期与结算

- **门店：先款后货**（现状保留）——财务审核节点校验「已收 ≥ 应收」，收满方可出库；
- **供应商：多账期模式**，抽象为三个字段：`settlement_type`（现结/月结/货到付款/预付）、
  `credit_days`（账期天数）、`settle_day`（月结日，如每月 25 日）；到期日 = 入库日/对账日 + 账期规则；
- 应付端据此生成**付款计划**与到期提醒，付款单核销对应采购入库；AI 预警超期未付/超期未收。

## 8. AI 智能（云端 DeepSeek，模型 `deepseek-flash`）

配置位置：`ai_api_key`（platform=`DeepSeek`，url=`https://api.deepseek.com`，api_key 存库**不入代码库**）
+ `ai_model`（platform=`DeepSeek`，model=`deepseek-flash`）。已实测：key 有效，`/models` 返回
`deepseek-flash` 与 `deepseek-v4-pro`；`chat/completions` 返回 200。注意该模型是**推理型**：
短 `max_tokens` 会被思考过程吃光（实测 16 token 全为 reasoning），配置时 `max_tokens` 建议 ≥ 2048。

三个抓手（按价值排序）：

1. **审核助手**（一期随审批流上线）：转账凭证 OCR 抽取金额/时间/付款方并与申报金额自动比对、差异高亮；
   供应链侧异常提示（数量偏离近三个月均值、超可用库存、超信用额度）；
2. **智能下单**（门店端 H5）：自然语言订货与补货建议 → 生成要货单草稿供确认（AiTool + AiWorkflow 编排）；
3. **经营问答与预警**：自然语言查应收/欠款/库存/销量，超期欠款、低库存、订量异动主动提醒；
   配套知识库（制度、价格政策、退货规则）。

**红线**：AI 只做建议与预处理，不得自动改金额、不得自动放行审批；每次输出留痕可追溯；
金额与客户信息外发需评估合规。

## 9. 路线图

| 阶段 | 内容 | 工期 | 验收标准 |
|---|---|---|---|
| Phase 0 | 主数据统一方案、价目与账期政策、单据链与审批节点、AI 场景清单、字段映射表 | 1–2 周 | 蓝图评审通过，字段映射与迁移脚本清单确定 |
| Phase 1 | BPM 要货审批（供应链→财务）+ 订单转 ERP 销售订单/销售出库 + 库存扣减 + 门店端进度 | 3–4 周 | 一张要货单从提交到出库全链路打通，库存准确变化 |
| Phase 2 | 应收与收款核销 + 门店对账/欠款台账 + 信用额度与账期校验 | 2–3 周 | 应收余额与收款逐笔可核销，对账单可导出 |
| Phase 3 | 采购链（申请/订单/入库）+ 应付与付款 + 供应商多账期 + 库存管理启用 | 3–4 周 | 采购到付款闭环，账期到期提醒准确 |
| Phase 4 | AI 三抓手（审核助手 → 智能下单 → 经营问答） | 3–4 周 | 审核提效可量化（审核时长/差错率） |
| Phase 5 | 凭证自动化（ERP 单据→FMS 凭证）、期初余额、报表模板、税务基础 | 4–6 周 | 凭证可查、期间可锁、报表与手工账核对一致 |
| Phase 6 | 数据迁移与双轨切换（期初库存/往来余额/未结单据/价目） | 2–3 周 | 与金蝶余额、库存对账为零差异后切换 |

合计约 **5–6 个月**（Phase 4 可与 2/3 并行）。

## 10. 数据迁移与双轨切换

1. 期初：库存（按 SKU + 批次/效期）、往来余额（应收/应付）、未结单据、商品价目、客户档案；
2. 双轨：商城/ERP 与金蝶并行一个完整账期，每日跑对账脚本（库存、应收、应付三项）；
3. 切换：金蝶转只读，保留历史查询；设"回退窗口"，期间发现差异可回切。

## 11. 风险与红线

- **财务合规**：三期之前金蝶仍是法定账，凭证/期间/审计留痕必须一次做对；
- **库存准确**：期初 + 出入库 + 盘点三者闭环，否则数据越用越乱；
- **双轨一致性**：对账脚本先行，差异定位流程要固化；
- **职责分离**：下单/审核/出库/收款/主数据维护分权，审批人按角色配置，避免越权查看；
- **AI 边界**：不自动改数、不自动放行；模型输出留痕；数据外发合规评估。

## 12. 待确认事项

1. 总账替代的时间点与合规口径（是否需要外部审计配合）；
2. 门店信用额度与账期是否全部"先款后货"，还是部分大客户给账期；
3. 供应商账期模式的清单（现结/月结/货到付款/预付各自适用规则与结算日）；
4. 商品主数据统一的切换窗口（是否需要停单维护）；
5. AI 场景优先级确认（审核助手是否一期就上）。
