# 门店订货流程链 · 全局设计

> 目标：把"门店订货"从「单点下单 + 人工核验」升级为**端到端可追溯的订货链**：下单 → 提交付款凭证 → 两级审批 →
> 库存分配 → 出库配送 → 签收 → 对账结算 → 客诉售后 → 待办通知，每一段都有明确状态、责任人与留痕。
> 依据：`金蝶业财意见收集表_供应链2026.9.21.xlsx`（贺玲 8 条、张新宇 6 条）+
> 本仓库实测现状。相关设计：[`organization-model.md`](./organization-model.md)（组织与一店三面）、
> [`delivery-price-list-design.md`](./delivery-price-list-design.md)（配送价与毛利）、
> [`kingdee-gap-requirements.md`](./kingdee-gap-requirements.md)（工作包）。

## 1. 现状链路（实测，含断点）

```
门店 H5 下单 ──► 扣商城 SKU 库存 ──► 线下转账 ──► 上传付款截图 ──► 供应链审批 ──► 财务审批(核收款) ──► 待发货 ──► ERP 配送出库 ──► 门店收货 ──► 完成
   (一店三面)      (product_sku.stock)  (转账)      (trade_order_payment_proof) (BPM 一级)      (BPM 二级)        (自动置位)    (回写已发货+收货单)  (差异台账)
> 注：商城后台**不再提供手工「发货」入口**——发货由 ERP 配送出库单审核承接（审核即回写订单「已发货」并生成
> 门店待确认收货单，门店确认后订单置「已完成」）；加盟门店未通过两级审批时，出库审核会被发货闸门拦下，
> 「订单状态」在审批通过前显示为「审核中」。
```

**已具备**（可直接复用，不必重做）：
- 付款凭证：`trade_order_payment_proof`（urls / amount / confirmed_amount / payer_name / transfer_time /
  status / audit_user_id / audit_time / audit_remark），**门店提交即按申报金额转"待发货"并进入两级审批**，
  审批通过 = 认定收款（confirmed_amount = 申报金额），审批驳回 = 门店重新上传（2026-09 起不再有后台「收款核验」步骤）；
- 订单操作留痕：`trade_order_log` + 操作类型枚举；改价 `update-price`、改地址 `update-address`、备注 `update-remark`；
- 发货与物流：门店要货由 **ERP 配送出库**承接（`ErpStoreDeliveryAuditedEvent` → 回写订单「已发货」+ 生成门店收货单）；
  商城侧原来的手工 `delivery` 接口（快递单号）已从后台订单列表/详情下线，仅保留接口备特殊场景；
- 商城库存：下单即扣 `product_sku.stock`（`TradeProductSkuOrderHandler` → `productSkuApi.updateSkuStock`），
  取消回滚；
- H5「再来一单」按当前价与库存重取（`useReorder.ts`）。

**断点（本次设计要补的）**：

| # | 断点 | 实测依据 |
|---|---|---|
| B1 | 订单**不归属组织/客户**：不知道是哪家店、记谁的账 | `trade_order` 只有 `user_id`；`member_user`/`erp_customer` 无 `dept_id` |
| B2 | **无审批链**：下单后没有供应链/财务审核环节 | mall 模块 **0 处 BPM 调用**；admin 仅有发货/核验/改价接口 |
| B3 | **两套库存**：商城 `product_sku.stock` 与 ERP `erp_stock`（只有在仓数量）互不联动 | `TradeProductSkuOrderHandler` vs `ErpStockDO` |
| B4 | **商城订单与 ERP 单据零联动**：销售订单/出库靠手工录 | 无 `erp-api`，trade 模块无 ERP 调用 |
| B5 | 无**在途/占用/待检**状态，无法回答"在仓+在途"真实可发量 | `erp_stock` 仅 productId/warehouseId/count |
| B6 | 无**缺货分配与补发单**：靠人工登记与单号后缀 | 无相关表 |
| B7 | 无**余款（预收款）台账**：钱包已归档，余款无处记 | `zz_deprecated_pay_wallet*`；无预收余额表 |
| B8 | 无**待办/通知**：状态推进无人被提醒 | `system_notify_message` 0 行；BPM 未接 |
| B9 | 客诉散落系统外，售后无"客诉"类型 | `trade_after_sale` 0 行且无客诉字段 |
| B10 | 无 PC 订货端与导出，门店对账靠手机截图 | 仅 H5 |

## 2. 目标链（九段）

```
[0 主数据] 门店(客户+dept+代理) · 配送价 · 结算模式 · 账期/信用
      ▼
[1 下单]  切换门店 → 取价 → 校验 → 生成订单（快照组织/客户/价格/地址）
      ▼
[2 付款]  先款后货：线下转账+凭证核验+余款入账 ｜ 月结：挂应收不阻塞
      ▼
[3 审核]  供应链审核（改量/拆行/指定收货仓/预计到货）→ 财务审核（到账/账期）
      ▼
[4 分配]  可用量 = 在仓 − 占用 + 在途 → 按提交顺序分配 → 不足则缺货登记 + 部分发货
      ▼
[5 出库]  ERP 销售出库（审核扣库存，支持分批 outCount）→ WMS/三方仓批次 → 物流
      ▼
[6 签收]  门店签收（少货/破损 → 客诉入口）→ 订单完成
      ▼
[7 对账]  应收/预收余款/账期到期 → 对账单 → 余款抵扣与折算 → 明细可查
      ▼
[8 客诉]  订单行提客诉（图/视频）→ 采购回复 → 下推退单/补发/预补货台账
      ▼
[9 通知]  每次状态迁移生成待办（责任人）+ 站内信
```

### 第 0 段 主数据前置（先决条件）

门店 = **一店三面**（`organization-model.md`）：dept 节点（组织/权限）+ `erp_customer`（结算模式、账期、
信用额度、默认配送价）+ `member_user`（H5 订货账号）；代理商（母客户）→ 多门店，H5 提供**门店切换器**。
配送价取自配送价目表版本（`delivery-price-list-design.md`）。

### 第 1 段 下单与校验

H5 下单时后端依次执行（任一失败即拦截并给出可读原因）：
1. **归属校验**：`dept_id`/`customer_id` 必须存在且状态正常（解决 B1，杜绝"下到别的店"）；
2. **取价**：按配送价目表版本取价（含税口径统一），**快照进订单行**；
3. **门槛校验**：起订量（缺字段，需新增）、包邮门槛（`trade_config` 现有关/0）、预估运费；
4. **信用与账期校验**：月结门店校验信用额度与逾期应收；
5. **余款校验**：显示可用余款并允许抵扣（第 2 段入账，第 7 段核销）；
6. **可用量校验**：按第 4 段口径给出"可发/缺货"提示（可下单但标记缺货，不硬拦）。
   → 生成 `trade_order`（新增强制字段：`dept_id`、`customer_id`、`settlement_mode`、`agent_customer_id`）。

### 第 2 段 付款（结算模式驱动）

| 模式 | 流程 | 系统行为 |
|---|---|---|
| **先款后货**（默认，符合现在线下转账）| 门店转账 → H5 上传凭证（金额/付款人/转账时间）→ **直接进入两级审批**（供应链 → 财务）| 申报金额 ≥ 应付 → 转"待发货"；审批通过即认定收款，**超出部分入余款台账**（解决 B7）；申报不足时由财务在审批中决定通过（差额挂往来）或驳回补款 |
| **月结** | 下单不付款 | 挂应收（账期起算日 + 到期日），不阻塞审核与发货；到期进账龄预警 |
| **余款抵扣** | 下单时选择使用余款 | 抵扣生成核销明细；不足部分仍需转账/挂账 |

凭证校验增强（对应需求 #16）：文件类型与大小限制 + 图片必须为转账截图（**OCR 关键词识别需外部 OCR 能力**，
当前 DeepSeek key 无视觉模型，先以"必传 + 财务在审批节点人工核对"兜底，R18-3）。

### 第 3 段 审核（BPM 混合式，按店型分流）

> **门店订货链 S1 已落地的分流规则**（来源：CY-001 重庆亚特餐饮整体业务流程泳道图）：
> 「加盟门店需财务审核进入订单工作台 / 直营门店则直接审核」——即**加盟店**要货在门店提交付款凭证后
> **自动**进入两级审批（供应链 → 财务出纳，BPM 流程定义 `trade-order-store-audit`；后台也可手工提交），
> **直营店免审**：提交凭证即进入待发货（审核状态留痕为「已通过 + 直营门店免审」），发货闸门对直营不设限。实现见
> `TradeOrderAuditServiceImpl#validateCanDelivery` 与 `TradeOrderUpdateServiceImpl#updateOrderPaidByOffline`；
> 店型取 `erp_customer.store_type`（DIRECT / FRANCHISE）。详见
> [`as-is-process-and-gaps.md`](./as-is-process-and-gaps.md)（§2 关键规则、G1）。
>
> 另：图上"订单工作台"是中心库侧的操作中枢，"分料属性（统配 / 直配）"是其分支条件 —— **S2 切片一已落地**，
> 见下方「第 3.5 段」；下单即分料（H5 端选统配/直拨）、缺货分配与门店收货仍属后续切片。
>
> **审批页的业务表单约定（2026-09-28 修复）**：BPM 的 `formCustomViewPath` 必须是**组件全路径**（如
> `/mall/trade/order/detail/modules/approval-summary.vue`），且该组件必须**接受 `id` 属性**
> （BPM 传入 `businessKey` = 订单编号），仅在缺省时回退路由参数 —— 与库内其他嵌入审批页同一范式。
> 早前把路由路径填进该字段、且详情页只读 `route.params.id`，导致嵌入审批页时
> `Number(undefined)=NaN`，后端报 `Failed to convert "NaN" to Long`。
> 现订单详情页已支持 `id` 属性 + NaN 兜底；审批页改用**只读摘要组件**（只展示门店/金额/收款/状态与商品行，
> 不暴露发货、核验等操作入口，避免审批人误操作）。
>
> **用接口手工改流程模型时，simpleModel 必须带全设计器字段**（2026-09-28 踩坑）：审批节点除
> `candidateStrategy/candidateParam/approveType/approveMethod/rejectHandler/timeoutHandler/assignEmptyHandler` 外，
> 还必须有 `fieldsPermission`、`buttonsSetting`（通过/拒绝/转办/委派/加签/退回 六项）以及
> `taskCreateListener / taskAssignListener / taskCompleteListener`（`{enable:false,path:null,header:[],body:[]}`）。
> 缺这些字段时流程模型在**流程设计器里打不开/无法编辑**（对比设计器自己生成的 `test` 模型字段即可发现）。
> 另：`/bpm/model/export` 对任何模型都返回空 bpmnXml，不能用来判断流程图数据是否完整。

**供应链审核**（必走）：可在审批中改数量/删行/拆分订单、指定收货仓与预计到货日；通过后**重算金额并快照应收**；
金额下降 → 差额入余款（或原路退回留痕），金额上升 → 补充付款要求。
**财务审核**（按结算模式）：先款后货核对到账与应收一致；月结校验信用额度。
**审批边界**：金额/数量偏离阈值内（可配，如 ±10%）供应链审核即放行；超阈值或新门店首单 → 加签财务/负责人。
（BPM 引擎已在库，落地方式是 `bpmProcessInstanceApi.createProcessInstance` + 监听
`BpmProcessInstanceStatusEvent`，与库内既有 BPM 接入同一套路。）

### 第 3.5 段 订单工作台与分料（统配 / 直拨）——S2 切片一，已落地

> 落地范围：**要货单（商城交易订单）→ 分料 → 生成 ERP 单据**这一段端到端可跑；库存口径未动。
> 数据脚本 `sql/local/33_workbench_alloc.sql`，页面 `views/mall/trade/workbench`，接口 `/trade/workbench/*`。

**物料属性（开关式，可同时开启，由工作台选）**：`erp_product.allow_central` / `allow_direct`
（默认都允许；演示数据里一次性用品只统配、鲜货只直拨，其余都允许）。产品表单与列表已带这两个开关。

**订单行分料**：`trade_order_item.alloc_mode`（`CENTRAL` 统配 / `DIRECT` 直拨；空 = 未分料）+
`alloc_count`（本次下推数量）。订单还新增 `store_type` 快照，工作台据此判定"直营免审"（不必跨模块 join
`erp_customer`）。

**工作台待处理口径**（`TradeOrderMapper#selectWorkbenchPage`）：订单状态 = 待发货(10) 且
（店型 ≠ FRANCHISE 或 `audit_status` = 20）且**至少一行未分料**；已全部下推的订单自动移出列表。

**下推落点**：

| 分料方式 | ERP 单据 | 单据平台类型 / 前缀 | 落表 | 说明 |
|---|---|---|---|---|
| 统配 CENTRAL | 配送出库单 | `DELIVERY_OUT` / XSCK… | `erp_sale_out` + `erp_sale_out_items` | 单据平台里"配送出库单"的编号前缀本就是 XSCK（`31_bill_platform_fix.sql` 已对齐），ERP 侧对应实体即销售出库单；审核后按 `SALE_OUT` 扣中心库在仓量 |
| 直拨 DIRECT | 采购订单 | `PURCHASE_ORDER` / CGDD… | `erp_purchase_order` + `erp_purchase_order_items` | 中心库向供应商下单、供应商直送门店（不入中心库）；供应商由工作台指定 |

下推一律：单据平台生成单号 → 写 `bill_relation`（源类型 `STORE_REQUISITION` 行级 → 目标单）→ 写 `bill_log`；
生成单据状态为**待审核**，本切片**不触发库存变动**（审核出库/入库才动库存）。

**幂等**：同一订单行重复下推被拒（`ORDER_WORKBENCH_PUSH_FAIL_ITEM_PUSHED`，提示已下推的目标单号）。
判据是"该行是否已有 bill_relation"，因为 `uk_bill_relation` 的唯一键含 `target_id`，
新目标单不会撞索引，唯一索引只能兜住"同目标单"的并发重复。

**商城 SKU ↔ ERP 物料**：用 `product_sku.bar_code = erp_product.bar_code` 对齐（种子数据即如此建），
不新增映射表；取不到物料时工作台明确提示"未对应 ERP 物料（条码 …），无法下推"。

**本切片没做的（后续）**：采购入库与门店收货（入库仓 = 门店）、门店库存账、库存四态（在仓/在途/待检/占用）
与可用量分配、缺货登记与补发、收货差异、工作台改量拆单与指定收货仓、待办通知；工作台"可发数量提示"
目前只表达"未下推数量"，真实可用量待库存四态落地。

> **更新（2026-09-29）**：门店收货（入库仓 = 门店）、门店库存账、收货差异**已落地**，见
> [`store-receipt-and-receivables-design.md`](./store-receipt-and-receivables-design.md)；
> 库存四态中的「在仓/占用/在途」已在工作台展示（库存中心切片一），缺货登记与补发、门店退货仍是后续切片。

### 第 4 段 库存分配（缺货与补发）

- 口径升级为**多状态库存**：`在仓 / 在途 / 待检 / 占用`，可用量 = 在仓 − 占用 + 在途（对应需求 #11/#13）；
- **分配规则**：按订单提交先后（先到先得）对可用量做占用；不足部分生成`缺货登记单`（按订单行去重、
  显式关联订单行，替代人工登记与"单号后缀"识别）；
- **部分发货决策**：可供数量 ≥ 起发比例（可配）则部分发货，剩余转补发；否则整单等待/压单，由供应链选择，
  两种选择都留痕并通知门店；
- 收货仓在订单行上指定（当前 `erp_purchase_in_items` 已有 `warehouse_id`，商城侧需补同构字段）。

### 第 5 段 出库与配送

商城审核通过 → **自动生成 ERP 销售订单** → ERP 销售出库（审核即扣 `erp_stock`，`outCount` 支持分批）
→ 出库单回写商城订单行"已出数量" → 物流（快递单号）或三方仓发货（WMS 批次）。
**补发单显式关联原单**（`source_order_id`/`source_item_id`），运费可关联原单（需求 #19）。
技术前提：新建 `juling-module-erp-api`，暴露销售订单/出库与库存查询（解决 B4）。

### 第 6 段 签收与完成 —— **S3 切片一已落地**

门店在 H5 确认收货（可登记少货/破损数量与图片）→ 订单完成；异常自动开客诉草稿并通知采购。
（当前有 `receive_time` 字段但无签收差异登记。）

> **已落地（2026-09-29）**：出库审核 → 自动转「已发货」+ 生成待确认收货单 → 门店 H5 / 后台代录确认收货
> → 实收数量按批次入**门店仓**（门店库存账）→ 差异金额调整**门店往来台账**（应收）→ 订单完成。
> 门店退货/调拨/盘点/报损、客诉下推仍是后续切片。详见
> [`store-receipt-and-receivables-design.md`](./store-receipt-and-receivables-design.md)。

### 第 7 段 对账与结算

新增**门店往来台账**：应收（月结）、预收余款、抵扣核销、折算记录，逐笔可查（解决 B7 与需求 #22 的核心痛点
"查不到余款的产生明细"）。订单页显示余款并提醒使用；对账单可按门店/期间导出。

### 第 8 段 客诉与售后

在订单行发起客诉（图片/视频、数量、赔付期望）→ 采购回复处理结果 → 系统下推：**补发单 / 预补货台账 /
退单（折余款或退款）**，结果回写订单行状态；全链路留痕，替代飞书与人工比对（需求 #8/#23）。

### 第 9 段 通知与待办

每次状态迁移生成待办：供应链（待审核、缺货决策）、财务（待审批核收款）、仓库（待出库、待补发）、
门店（待付款、待签收、余款提醒、客诉回复）；PC 与 H5 双端待办中心 + 站内信（`system_notify_message`）。

## 3. 状态机（订单主状态 × 各段子状态）

**订单主状态**（沿用现有，不破坏既有数据）：`0 待付款 → 10 待发货 → 20 已发货 → 30 已完成 / 40 已取消`。
**新增业务子状态**（不改主状态语义）：
- 审核：`待供应链审核 / 待财务审核 / 审核通过 / 驳回`（BPM 实例状态映射）；
- 库存：`待分配 / 部分分配 / 已分配(缺货) / 已备货`；
- 出库：`待出库 / 部分出库 / 已出库`（与 `outCount` 对应）；
- 结算：`待付款 / 部分到账 / 已到账 / 已挂账 / 余款已抵扣`；
- 客诉：`无 / 处理中 / 已补发 / 已退款 / 已折余款 / 已关闭`。

## 5. 分期与验收

| 阶段 | 内容 | 端到端验收场景 |
|---|---|---|
| **S1 归属与审核**（1.5–2 周）| 一店三面绑定 + 代理商门店切换 + 订单快照组织/客户 + 供应链/财务 BPM 审核 + 待办通知 | 代理账号切换门店下单 → 订单归属正确 → 门店上传付款凭证（自动进审批）→ 供应链改量 → 重算应收 → 财务审批认定收款 → 待发货 |
| **S2 库存与出库联动**（2 周）| 多状态库存 + 分配/缺货登记 + 商城审核通过自动生成 ERP 销售订单与出库 + 部分出库回写 | 库存不足 → 自动缺货登记 → 部分发货 → 补发单关联原单 → 库存与出库单一致 |
| **S3 结算与余款**（1.5 周）| 结算模式（先款后货/月结）+ 预收余款台账与抵扣 + 对账单 | 多付 → 余款入账 → 下次下单抵扣 → 台账逐笔可查；月结门店超额度被拦截 |
| **S4 客诉闭环与门店端增强**（2 周）| 客诉单 + 下推补发/预补货/退单 + PC 订货端与导出 + 签收差异登记 | 订单行提客诉 → 采购回复 → 自动补发 → 门店签收 → 报表可见客诉与销售关联 |
