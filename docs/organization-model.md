# 组织与主体模型（加盟店 / 公司 / 仓库 / 供应商）

> 背景：供应商主数据需求中"合同签订了哪几个组织"里的**组织**指什么？本文件给出核实后的结论与落地模型。
> 相关：[`docs/supplier-master-data-design.md`](./supplier-master-data-design.md)、
> [`docs/intelligent-system-blueprint.md`](./intelligent-system-blueprint.md)。

## 1. 结论：组织 = `system_dept` 部门树上的节点，不新建"组织档案"表

因为库里已经在这么用了（实测数据）：

| 层级 | 节点 |
|---|---|
| 品牌 / 板块 | 119 萍姐、120 直营门店、121 中心库、122 卤校长 |
| 公司（= 签约主体）| 128 重庆萍姐品牌管理公司、129 成都萍姐管理公司、130 PJ公司、131 亚特萍姐商贸公司、132 萍婷商贸公司、133 PT公司；123 范陈企业管理公司、124 涵宇森商贸公司、125 大晟晟商行、126 HYS公司 |
| 职能部门 | 131 亚特萍姐商贸公司 → 147 供应链 → 161 供应链前端 / 162 供应链后端 / **163 采购** |
| 门店（加盟店 / 直营店）| 134–146 共 **13 家**：耙二哥双碑店、耙二哥新牌坊店、耙二哥冉家坝店、卤校长杨家坪店/观音桥店/沙坪坝店/广州店、渝凤凰沙坪坝店、萍姐观音桥、萍姐成都、成都杨老头、长安亭深圳店、成都地摊火锅 |
| 仓库节点 | 121 中心库 → 127 雷森企业管理公司 |

旁证：全库**没有任何组织/公司/法人表**（唯一 4 张 `%org%` 表是 Flowable 的 `act_ru_identitylink` 等身份链接表）。
所以部门树就是本系统唯一的组织载体，"采购部门"在库里也确实是真实节点（dept 163）。

## 2. 四种主体各归其位（不要混在一张表）

| 主体 | 承载表 | 角色 |
|---|---|---|
| 亚特本方组织（品牌 / 公司 / 部门 / 门店节点）| `system_dept` | 权限归属、审批归属、**签约主体** |
| 加盟店（经营与结算对象）| `system_dept` 节点 + `erp_customer` | 亚特对加盟店 ≈ **经销商/批发客户**：账期、信用额度、配送价、赊账 |
| 第三方供应商（供货方）| `erp_supplier`（+ 本文档同期的扩展设计）| 采购来源；**不入部门树**，避免污染权限与审批树 |
| 仓库（履约地点）| `erp_warehouse`（需补 `dept_id` + `type`）| 亚特自有仓（公司仓库 / 中心库）、未来三方仓、供应商直发 |

## 3. 加盟店 = 一店三面（当前是断的，必须补绑定）

现状实测：`trade_order` 只有 `user_id`（商城会员），**没有 dept_id / customer_id**；`erp_customer` 没有
`dept_id`，与 `member_user` 之间无任何关联；`member_user` 也没有 `dept_id`。
也就是说今天"给加盟店开账号去 H5 订货"在数据上是**断链**的：下了单系统既不知道是哪家店，也不知道该记谁的账。

设计（一面一张表，用外键互相绑定，**不把业务字段塞进 `system_dept`**，便于跟随上游升级）：

1. **组织面 = dept 节点**（例：134 耙二哥双碑店）——负责权限、审批归属、报表归属；
2. **经营面 = `erp_customer`**（蓝图 4.2）——补 `dept_id` 指向门店节点，并承载店型（直营/加盟）、结算方式、
   账期、信用额度、默认配送价、收货地址、联系人；
3. **账号面 = `member_user`**（H5 订货账号）——补 `dept_id` / `customer_id`（或在 `erp_customer` 存
   `member_user_id`）；下单时把 `dept_id + customer_id` **快照**进 `trade_order`，一家店一单一归属，
   事后改绑不影响历史单据。

补上这三面，才能支撑：门店维度的要货审批、账期与信用额度校验、按店的配送价、门店对账与报表。

### 3.1 还要补一层「代理商」（来自门店订货方反馈）

实际业务里**一个代理/经销商同时在多个品牌下拥有多家门店**（例：同一代理同时有卤校长、萍姐(PT)、
萍姐(一企创) 的门店），而当前模型只有"门店节点 + 单个 `erp_customer`"，缺少中间层。因此：

- `erp_customer` 增加**主体层级**：代理商（母）→ 门店（子），即 `parent_customer_id`；代理商层面管账期、
  信用额度与结算，门店层面管收货地址与订货人；
- 一个代理多门店 → H5 需要**门店切换器**（当前切换靠各自账号，容易把 A 店的货下到 B 店，门店订货方
  已明确反馈"没有切换会下错店"）；订货账号登录后按门店属性**自动下推组织**，门店无感；
- 多品牌（卤校长 / 萍姐 PT / 萍姐一企创 / 杨老头 / 耙二哥 / 直营）究竟是**多租户**（数据隔离，系统现有
  亚特、亚特餐饮 2 个租户）还是**同租户下的品牌维度**（组织树分组），直接决定"统一账号自动下推"怎么实现，
  需确认（见第 6 节）。

## 4. 对本方签约主体的影响（供应商合同落点）

`erp_supplier_org_contract.org_id` → **`system_dept.id`**，指向公司层节点（128 / 131 / …），
即"这份供应商合同由亚特哪个主体签的、签了几家"；客户协议同理挂门店节点。
**原设计文档第 6 节待确认 #1 由此关闭**，不需要新建"组织"表。

## 5. 仓库与第三方供应商寻源

- `erp_warehouse` 补 `dept_id`（归属组织，如 121 中心库）与 `type`（自有仓 / 三方仓 / 供应商直发），
  默认仓已有 `default_status`；
- 供应商侧补**寻源维度**：可供品类/商品、报价（与采购价格历史设计同一本账联动）、准入与淘汰状态，
  支撑"挖掘第三方供应商"；
- 加盟店订货的履约路径要能二选一：**中心库出库**或**供应商直发**（出库/入库单标记履约仓与来源），
  供应商账期在蓝图二期的采购链里补。

## 6. 待确认

1. 13 家门店目前挂在名为"**直营门店**"的节点（dept 120）下，但业务上你说的加盟店"类似经销商"。
   需确认这 13 家是**直营**、还是**加盟**（或两者都有），这决定 `erp_customer` 的店型默认值，
   以及账期/信用额度是否对全部门店生效。两类都有就在门店节点下各建一个分组节点，无需改表结构。
2. **多品牌是多租户还是品牌维度**（见 3.1）：系统现有 2 个租户（亚特 / 亚特餐饮），而业务上有卤校长、
   萍姐(PT)、萍姐(一企创)、杨老头、耙二哥、直营等多个品牌组织。"统一账号自动下推组织"的实现方式取决于此。
