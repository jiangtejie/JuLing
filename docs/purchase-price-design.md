# 采购价目表设计

> 来源：用户提出「系统里需要增加采购价目表列表，参考金蝶的字段，对后期财务核算成本有很大作用」。
> 相关：[master-data-unified-design.md](./master-data-unified-design.md)（主数据统一）、
> [supplier-master-data-design.md](./supplier-master-data-design.md)（供应商档案）。
> 状态：**一期已落地**（[sql/local/65](../sql/local/65_purchase_price.sql)）。

## 1. 为什么需要它（先说清价值，再说设计）

### 1.1 现状：价格的表达能力只有一个字段

`erp_product.purchase_price` —— **一个物料一个采购价**。前端选物料时直接
`row.productPrice = product.purchasePrice || 0`。所以今天表达不了采购天天遇到的三件事：

| 需求 | 现状 |
|---|---|
| 同一物料**不同供应商不同价** | ❌ |
| 同一供应商**调价**（带生效/失效日期） | ❌ 改了就改了，没有历史 |
| **量大价优**（阶梯价） | ❌ |

### 1.2 后果：错的价会一路进到存货成本

实测的成本链路（这是「对财务核算成本有很大作用」的具体含义）：

```
采购订单行 product_price
  → 采购入库行 product_price（从订单带出）
  → ErpPurchaseInServiceImpl:247   inReqBO.setUnitCost(purchaseInItem.getProductPrice())
  → ErpStockBatchServiceImpl:129   batch.setUnitCost(unitCost)
  → 出库/领用成本 = batch.unit_cost × qty
```

**采购单价直接决定存货成本。** 而今天这个价只有一个来源（物料主数据上的单值），
采购下单只能**手工改价** —— 改错的价没有依据可查、也没有事后比对。价目表就是让订单价有据可依。

> 需要说清的边界：价目表**不直接参与成本计算**（存货成本走批次实际成本）。
> 它的作用是保证**订单价的准确性**，从而间接保证入库成本正确。
> 真正意义的「标准成本 vs 实际成本差异分析」需要发票/暂估模块，**当前系统没有**。

## 2. 数据模型

对齐金蝶的「价目表 + 价目表明细」。金蝶列表页把表头属性（币别/供应商/单据状态/含税/默认价目表/
生效日期/失效日期）**在每一行重复展示** —— 这是表头被拍平，说明底层是主从结构。

### 2.1 `erp_purchase_price`（头）

| 列 | 说明 |
|---|---|
| `code` | 业务编码，走编码规则 `erp_purchase_price`（前缀 `CJJM`） |
| `name` | 价目表名称 |
| `supplier_id` | 供应商；**为空 = 通用价目表**（不限供应商） |
| `is_default` | 默认价目表（同层级内取价优先） |
| `status` | 启用 / 停用（仅启用中的参与取价） |
| `effective_date` / `expiry_date` | 有效期；为空表示不限 / 长期有效 |

### 2.2 `erp_purchase_price_item`（行）

| 列 | 说明 |
|---|---|
| `price_id` | 头编号 |
| `product_id` | 物料 |
| `from_qty` / `to_qty` | 数量区间（半开 `[from, to)`）；为空表示无界 —— 这就是阶梯价 |
| `price` | **单价（不含税，权威值）** |
| `tax_percent` | 税率(%) |

### 2.3 两处**有意收敛**（不照搬金蝶）

1. **不存「含税单价」**。金蝶存 `单价` + `含税单价` + `税率%` 三个，其中一个是冗余的，
   两处存必然漂移。改为只存不含税单价 + 税率，含税单价是**计算值**（界面仍可录含税价，自动换算）。
   与本仓库订单行的 `productPrice / taxPercent / taxPrice` 口径一致。
2. **不要「计价单位」列**。金蝶有它是因为一个物料可多单位；本系统 `erp_product` 只有一个
   `unit_id`，计价单位由物料决定，展示时取物料的单位即可。

## 3. 取价算法（核心）

`ErpPurchasePriceService#matchPrice(supplierId, productId, quantity, date)`

**过滤**：价目表已启用 + 当日落在有效期内 + 物料匹配 + 数量落在 `[fromQty, toQty)` +
（供应商专项要求精确匹配；通用价目表谁都适用）

**排序取第一条**：

1. **供应商专项** 优先于 通用
2. **默认价目表** 优先
3. **生效日期** 新的优先
4. **阶梯档位** 高的优先（`from_qty` 大者）

**兜底**：都没命中时取 `erp_product.purchase_price`（老数据不失效），
此时返回结果的 `source = PRODUCT`。

**实现方式**：先按物料查出候选行，再一次性取回这些行的表头，在内存里过滤排序 ——
数据量小，比拼多层 join 的 SQL 更容易读懂，也避免多租户拦截器对原生 SQL 的干扰。

## 4. 与采购订单的集成

沿用「**后端为权威 + 前端给即时反馈**」的分工（与供应商交易条件那轮一致）：

| 侧 | 行为 |
|---|---|
| **后端** | 建单/改单时，订单行的单价**为空**才取价；税率取「价目表行上的税率 &gt; 供应商的开票税点」 |
| **前端** | 选物料时调 `/erp/purchase-price/match` 带出单价与税率，用户看得见 |

**取价只在单价为空时触发** —— 用户既然已经把单价填了，就不该再替他改税率，
否则「我明明填了价，税率怎么变了」很难解释。这就是「允许按单覆盖」。

**订单只存快照价，不引用价目表 id**：价目表改了历史订单不受影响；也因此价目表**删除无需引用校验**。

## 5. 归口与权限

- 菜单挂在「**基础资料 → 公共资料**」（与物料单位、仓库信息、结算账户同层）——
  它是采购/财务都要引用的价格主数据，符合「主数据集中维护、子系统引用」的归口。
  **金蝶放在采购管理下，这里是有意不同**。
- 权限 `erp:purchase-price:query|create|update|delete|export`；
  `/match` 端点**故意不加 @PreAuthorize** —— 它是采购订单录入时的辅助取价，
  与 `simple-list` 同性质，若要求 `erp:purchase-price:query` 会导致只有订单权限的采购员取不到价。

## 6. 顺带修复：物料主数据缺业务编码

做这个功能时发现：客户 / 供应商 / 仓库 / 计量单位 / 商品**五个主数据都有业务编码**，
唯独 **物料（`erp_product`）漏了**。而金蝶价目表里「物料编码」正是行的主标识，
没有它价目表只能显示名称，同名物料无法区分。

已在同一个脚本的第 6 节按同一套机制补上（规则表 + `code` 列 + 回填 + 唯一索引，前缀 `WL`）。

> **待处理**：`product_spu`（商城商品）的编码规则也用了 `WL` 前缀。
> 两套目录合并时应把商城侧改成 `SP`（商品），否则两边都发 `WL000001`，肉眼无法区分。
> 当前两表数据都为空，改动无成本。

## 7. 分期

| 期 | 内容 | 状态 |
|---|---|---|
| **一期** | 表 + 编码规则 + 菜单权限 + 后端 CRUD + 取价算法 + 前端主从维护页 + 采购订单带出价 | **已落地** |
| 二期 | 价格控制（订单价偏离价目表超阈值告警/拦截）、变更留痕、采购价格分析报表 | 待做 |
| 三期 | 多币别、按组织（需求组织/采购组织）—— 依赖还没定的多组织模型 | 待做 |

## 8. 一处没照搬金蝶的地方

金蝶的**扁平列表**（头和行拍平、每行重复供应商/状态/有效期）在数据量大时不好用。
这里列表页展示**价目表（头）**，点进去看明细行 —— 与采购订单等页面一致。
如果更想要金蝶那种「一眼看全部价格」的效果，可以再加一个扁平视图，说一声即可。

## 9. 待确认

1. 采购订单的**打印模板**要不要体现取价来源（哪张价目表）。
2. 二期做价格控制时，「偏离多少算异常」的阈值需要业务给数。
3. 价目表的**变更留痕**：当前没有，改价后无法追溯谁在什么时候改了什么。
