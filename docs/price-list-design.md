# 价目表设计（采购 + 配送）

> 来源：用户提出「系统里需要增加采购价目表列表，参考金蝶的字段，对后期财务核算成本有很大作用」。
> 相关：[master-data-unified-design.md](./master-data-unified-design.md)（主数据统一）、
> [supplier-master-data-design.md](./supplier-master-data-design.md)（供应商档案）。
> 状态：**一期已落地**（[sql/local/65](../sql/local/65_purchase_price.sql)）。

## 1. 为什么需要它（先说清价值，再说设计）

### 1.1 现状：价格的表达能力只有一个字段

`erp_product.purchase_price` —— **一个物料一个采购价**。前端选物料时直接
`row.productPrice = product.purchasePrice || 0`。所以今天表达不了采购天天遇到的三件事：

| 需求 | 现状 |
|---|---|
| 同一物料**不同供应商不同价** | ❌ |
| 同一供应商**调价**（带生效/失效日期） | ❌ 改了就改了，没有历史 |
| **量大价优**（阶梯价） | ❌ |

### 1.2 后果：错的价会一路进到存货成本

实测的成本链路（这是「对财务核算成本有很大作用」的具体含义）：

```
采购订单行 product_price
  → 采购入库行 product_price（从订单带出）
  → ErpPurchaseInServiceImpl:247   inReqBO.setUnitCost(purchaseInItem.getProductPrice())
  → ErpStockBatchServiceImpl:129   batch.setUnitCost(unitCost)
  → 出库/领用成本 = batch.unit_cost × qty
```

**采购单价直接决定存货成本。** 而今天这个价只有一个来源（物料主数据上的单值），
采购下单只能**手工改价** —— 改错的价没有依据可查、也没有事后比对。价目表就是让订单价有据可依。

> 需要说清的边界：价目表**不直接参与成本计算**（存货成本走批次实际成本）。
> 它的作用是保证**订单价的准确性**，从而间接保证入库成本正确。
> 真正意义的「标准成本 vs 实际成本差异分析」需要发票/暂估模块，**当前系统没有**。

## 2. 数据模型

对齐金蝶的「价目表 + 价目表明细」。金蝶列表页把表头属性（币别/供应商/单据状态/含税/默认价目表/
生效日期/失效日期）**在每一行重复展示** —— 这是表头被拍平，说明底层是主从结构。

### 2.1 `erp_price_list`（头）

| 列 | 说明 |
|---|---|
| `price_type` | 价目表类型：`PURCHASE` 采购 / `DELIVERY` 配送（见 §12 的统一重构） |
| `code` | 业务编码，走编码规则（采购 `CJJM` / 配送 `PSJM`） |
| `name` | 价目表名称 |
| `price_includes_tax` / `pricer_user_id` | 报价口径 / 定价员（见 §10.1） |
| `status` | 启用 / 停用（仅启用中的参与取价） |
| `effective_date` / `expiry_date` | 有效期；为空表示不限 / 长期有效 |

### 2.2 `erp_price_list_item`（行）

| 列 | 说明 |
|---|---|
| `price_id` | 头编号 |
| `product_id` | 物料；**同一价目表里不可重复**（见 §11） |
| `price` | **单价（不含税，权威值）** |
| `tax_percent` | 税率(%) |

> 原先还有 `from_qty` / `to_qty`（数量区间，做阶梯价）—— 已去掉，原因见 **§11**。

### 2.3 两处**有意收敛**（不照搬金蝶）

1. **不存「含税单价」**。金蝶存 `单价` + `含税单价` + `税率%` 三个，其中一个是冗余的，
   两处存必然漂移。改为只存不含税单价 + 税率，含税单价是**计算值**（界面仍可录含税价，自动换算）。
   与本仓库订单行的 `productPrice / taxPercent / taxPrice` 口径一致。
2. **不要「计价单位」列**。金蝶有它是因为一个物料可多单位；本系统 `erp_product` 只有一个
   `unit_id`，计价单位由物料决定，展示时取物料的单位即可。

## 3. 取价算法（核心）

`ErpPriceListService#matchPrice(priceType, partnerId, productId, date)`

**过滤**：类型匹配 + 已启用 + 当日落在有效期内 + 物料在明细里 + 适用范围命中该对象（含通用范围）

**排序取第一条**：

1. **默认价目表** 优先（标在**适用范围行**上，见 §12）
2. **生效日期** 新的优先
3. **编号大** 优先（保证结果稳定，不依赖数据库返回顺序）

**兜底**：都没命中时取 `erp_product.purchase_price`（老数据不失效），
此时返回结果的 `source = PRODUCT`。

**实现方式**：先按物料查出候选行，再一次性取回这些行的表头，在内存里过滤排序 ——
数据量小，比拼多层 join 的 SQL 更容易读懂，也避免多租户拦截器对原生 SQL 的干扰。

## 4. 与采购订单的集成

沿用「**后端为权威 + 前端给即时反馈**」的分工（与供应商交易条件那轮一致）：

| 侧 | 行为 |
|---|---|
| **后端** | 建单/改单时，订单行的单价**为空**才取价；税率取「价目表行上的税率 &gt; 供应商的开票税点」 |
| **前端** | 选物料时调 `/erp/purchase-price/match` 带出单价与税率，用户看得见 |

**取价只在单价为空时触发** —— 用户既然已经把单价填了，就不该再替他改税率，
否则「我明明填了价，税率怎么变了」很难解释。这就是「允许按单覆盖」。

**订单只存快照价，不引用价目表 id**：价目表改了历史订单不受影响；也因此价目表**删除无需引用校验**。

## 5. 归口与权限

- 菜单挂在「**基础资料 → 公共资料**」（与物料单位、仓库信息、结算账户同层）——
  它是采购/财务都要引用的价格主数据，符合「主数据集中维护、子系统引用」的归口。
  **金蝶放在采购管理下，这里是有意不同**。
- 权限 `erp:price-list:query|create|update|delete|export`（采购与配送**共用**，见 §12）；
  `/match` 端点**故意不加 @PreAuthorize** —— 它是采购订单 / 门店订货录入时的辅助取价，
  与 `simple-list` 同性质，若要求 `erp:price-list:query` 会导致只有订单权限的人取不到价。

## 6. 顺带修复：物料主数据缺业务编码

做这个功能时发现：客户 / 供应商 / 仓库 / 计量单位 / 商品**五个主数据都有业务编码**，
唯独 **物料（`erp_product`）漏了**。而金蝶价目表里「物料编码」正是行的主标识，
没有它价目表只能显示名称，同名物料无法区分。

已在同一个脚本的第 6 节按同一套机制补上（规则表 + `code` 列 + 回填 + 唯一索引，前缀 `WL`）。

> **已处理**（[脚本 66](../sql/local/66_cleanup_loose_ends.sql)）：商城侧 `product_spu` 的前缀已由 `WL` 改为 `SP`，
> 规则名同步改为「商品编码」。当时两表都是 0 行、`current_value` 都是 0，改动零成本。
> 现在 ERP 物料发 `WL000001`、商城商品发 `SP000001`，两套目录在编码上也区分开了。

| 三期 | 多币别、按组织（需求组织/采购组织）—— 依赖还没定的多组织模型 | 待做 |

## 8. 一处没照搬金蝶的地方

金蝶的**扁平列表**（头和行拍平、每行重复供应商/状态/有效期）在数据量大时不好用。
这里列表页展示**价目表（头）**，点进去看明细行 —— 与采购订单等页面一致。
如果更想要金蝶那种「一眼看全部价格」的效果，可以再加一个扁平视图，说一声即可。

## 9. 待确认

1. 采购订单的**打印模板**要不要体现取价来源（哪张价目表）。
2. 二期做价格控制时，「偏离多少算异常」的阈值需要业务给数。
3. 价目表的**变更留痕**：当前没有，改价后无法追溯谁在什么时候改了什么。

## 10. 金蝶字段对照（第二轮吸纳）

用户提供金蝶「采购价目表 - 查看」界面，要求把常用字段吸纳过来。逐项对照后的取舍：

### 10.1 吸纳 3 项（[脚本 67](../sql/local/67_purchase_price_kingdee_fields.sql)）

| 字段 | 落点 | 说明 |
|---|---|---|
| **含税** | `price_includes_tax` | 供应商报价习惯直接报含税价（"13 个点"），整表统一口径比逐行按计算器贴合实际 |
| **定价员** | `pricer_user_id` | 与 `BaseDO.creator` 区分：常见是采购经理定价、文员录入，**责任人不等于录入人** |
| **规格型号** | 明细展示，**不落库** | 取物料的 `erp_product.standard`，与「计价单位」同理 |

**关于「含税」的一处关键设计**：行上的 `price` **恒为不含税**（权威、无歧义）——
这个标记记录的是「报价方当时怎么说的」，只影响录入方向。
界面把「单价(不含税)」与「含税单价」做成**两列可互算**（改任一个另一个自动跟着变），
所以无论供应商报哪种口径，录入都不用按计算器，而后端只有一个权威值可存。

### 10.2 不吸纳 5 项及理由

| 金蝶字段 | 不吸纳的理由 |
|---|---|
| **币别** | 本系统没有汇率表，`erp_purchase_order` 也没有币别，加了就是一个永远显示 CNY 的摆设，反而让人以为支持外币。真要进口采购，需要**先建汇率与多币别结算**，不是加一个字段 |
| **采购组织** | 组织维度一旦加上，就必须回答"取价时按哪个组织过滤"，而组织模型（品牌/门店/仓库怎么挂）**至今未定**（见 [organization-architecture-design.md](./organization-architecture-design.md)）。现在加会做出一个半成品的组织隔离，**比不加更危险** |
| **单据状态**（草稿/已审核） | 一期不做审批流，用 `status`（启用/停用）+ 生效·失效日期控制，与本仓库其它 ERP 主数据（客户/供应商/物料）一致 |
| **价格类型**（采购） | 本表就是采购价目表，类型恒定，字段冗余 |
| **价目表对象**（按物料/按分类） | 一期只支持按物料定价；按分类批量定价是独立特性，留二期 |
| **价外税** | 本系统本来就是「不含税单价 + 税率」模型，**等同于价外税**，无需字段 |

### 10.3 顺带核对：金蝶已有、我们也已有的字段

采购组织之外的：编码 ✓、供应商 ✓、名称 ✓、默认价目表 ✓、生效日 ✓、失效日 ✓、备注 ✓、
序号 ✓、物料编码 ✓、物料名称 ✓、计价单位 ✓、从（数量区间）✓。

## 11. 去掉「数量区间」（阶梯价）—— 一个"填了也不生效"的字段

用户问「数量从 / 数量至 是不是没用」。核实后：**确实没用，但根因是实现的缺口，不是功能本身没价值。**

### 11.1 为什么它不生效

| 环节 | 实际行为 |
|---|---|
| 前端 | 只在**选物料那一刻**取一次价（`matchPurchasePrice` 传的是当时行上的数量，默认 1）；**数量单元格没有任何 change 处理** |
| 后端 | 只在「单价为空」时取价 —— 而前端已经填了价，所以后端**不会再按真实数量取** |

于是实际路径是：选物料（数量 1）→ 取到第 1 档的价 → 用户把数量改成 100 → 保存 → **存进去的是第 1 档的价**。

### 11.2 为什么选择去掉，而不是修好

要让它真正生效，前端需要引入「这一行的价是**自动带出的**还是**手工改过的**」这份隐藏状态，
并在数量连续变化时处理异步竞态（后发的请求可能先返回）。成本不小，
而收益 —— 餐饮采购按数量分档定价 —— 并不明确。

**更关键的是：留着一个填了却不生效的字段，比没有这个字段更糟** ——
用户会以为分档定价生效了，实际拿到的是错价，而且没有任何提示。

### 11.3 连带的设计后果（重要）

去掉数量区间后，**同一价目表里同一物料只能有一行** ——
否则取价时两条都命中，取哪条取决于排序细节。

所以校验规则由「数量区间不重叠」换成了「**同一物料不可重复**」
（错误码 `1_030_104_001` 改为 `PURCHASE_PRICE_ITEM_PRODUCT_DUPLICATE`）。
这不是削弱校验，而是**把同一个不变量换成了新模型下的正确形式**。

取价算法同步简化为：供应商专项 > 通用 → 默认价目表 > 普通 → 生效日期新 > 旧。

### 11.4 如果以后真的需要阶梯价

数据结构上加回两列不难（比删列容易），真正的工作量在**前端**：
必须解决「自动价 vs 手工价」的判定与异步竞态。到时候建议直接用金蝶的做法
（明细行的「从 / 至」两列 + 取价时按 `fromQty` 倒序取中到的那一档）。

## 12. 统一重构：采购价目表 + 配送价目表 → 一套「价目表 + 类型」

**脚本**：[sql/local/69](../sql/local/69_unify_price_list.sql)（连跑 2 次结果一致）

### 12.1 为什么统一

用户提出要「配送价目表」（中心库 → 门店的内部结算价），并要求重构干净。逐项对照后发现两者
**除了"适用对象是谁"之外 90% 同构**：头字段相同、行字段相同、**取价算法完全相同**。
分成两张表 = 一份永远要同步维护的重复逻辑，而"销售价目表"迟早还会来。
当时采购侧**零生产数据**，是最便宜的迁移时机。

| | 采购价目表 | 配送价目表 |
|---|---|---|
| 适用对象 | 供应商 | **门店**（可选多个） |
| 取价 | 伙伴 + 物料 + 日期 | 同左 |
| 头/行字段 | — | **完全相同** |

### 12.2 三张表

- `erp_price_list`（头）：`price_type` 区分类型
- **`erp_price_list_scope`（适用范围，新表）**：一张价目表可适用 **N 个对象**；
  `partner_id` 为空 = **通用范围**（不限对象，优先级最低）
- `erp_price_list_item`（行）

**两处关键设计：**

1. **`is_default` 放在适用范围行上，不在头上**（对齐金蝶）——
   同一张价目表**只对部分门店默认**时粒度更准；放头上只能整张表一刀切。
2. **"通用范围"用 `partner_id IS NULL` 表达**，不另设字段 —— 一个机制覆盖两种情况。

编码规则：采购 `CJJM`、配送 `PSJM`（金蝶配送价目表也是 PSJM 前缀）；权限统一为 `erp:price-list:*`。

## 13. 配送价目表接入门店订货链

这是让配送价目表**真正起作用**的一步。完整链路：

```
门店 H5 下单
  → TradePriceServiceImpl：先用配送价目表(门店 + 物料)定价，没命中才用 SKU 价
  → trade_order_item.price
  → 门店收货 TradeStoreReceiptServiceImpl:355  setUnitCost(item.getPrice())
  → 门店库存成本
```

**三个必须知道的点：**

1. **算价必须拿到门店** —— 原先 `createOrder` 里算价在前（144 行）、解析门店在后（186 行），
   已把 `resolveStore` 提前；`settlementOrder`（结算预览）同样先解析，**保证下单页看到的价格与落单价一致**。
2. **SKU ↔ 物料靠 `barCode` 字符串对应**（复用 `TradeOrderWorkbenchServiceImpl:137` 的既有约定）。
   **任何一步拿不到就保持 SKU 价**（条码没维护 / 物料不存在 / 价目表没命中）——
   不能因为价目表没配好就让门店下不了单。
3. **单位换算**：价目表存的是**元**，而 `trade_order_item.price` 是**分**。

### 13.1 三层兜底（排查价格问题时必须记得）

```
配送价目表  →  erp_product.sale_price  →  商城 SKU 价
```

三层套在一起，"为什么是这个价"不容易一眼看出来。功能上是对的（保证下得了单），
但**排查时要逐层确认**。

顺带：`erp_product.sale_price` 此前是**全代码库没有任何消费方**的孤儿字段，
现在承担了「没维护配送价目表时的默认配送价」。

## 14. 遗留与风险

| 项 | 说明 |
|---|---|
| **适用范围的「逐行默认」界面** | 数据库已支持（`is_default` 在范围行），界面暂为整张表一个开关。金蝶那一列是逐行的 |
| **`matchPrice` 逐项调用** | 20 行订单约 60 次查询。功能没问题，但下单链路变重了 |
| **条码是隐式约定** | 条码没维护的物料会**静默回退到 SKU 价** —— 不报错，但也享受不到配送价，且无任何提示。建议扫一遍条码质量 |
| **配送价定价未经真实下单验证** | 代码链路与编译都通过，但**没有真实下过单** |
